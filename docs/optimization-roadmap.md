# Agents on Duty 企业化优化路线图

## 目标

**阶段完成定义：代码实现、测试入库、CI 通过、文档同步且 PR 已合并。**本地跑通不能代替 CI 和合并。

把当前的客服 Agent Demo 收敛成一个可演示、可恢复、可审计的售后业务系统。

不继续堆 Agent 数量或框架名词，先把一条业务闭环做深：

```text
用户申请退款
  → Agent 查询订单并校验条件
  → 需要人工时暂停
  → 工单进入客服工作台
  → 客服批准、拒绝或要求补充信息
  → Agent 恢复执行
  → 幂等调用退款服务
  → 返回结果并写入审计记录
```

## 修改顺序

### 阶段一：退款/售后业务闭环

退款申请、撤回、归属校验和防重复提交的演示能力已合并，相关测试与 CI 已通过。订单为模拟数据，不执行真实退款。

- [x] 定义订单、退款申请和工单状态机。
- [x] 定义退款条件、拒绝原因和人工审批条件。
- [x] 增加订单归属校验，用户只能访问自己的订单。
- [x] 将 mock 工具整理成稳定业务 API，明确输入、输出和错误码。
- [x] 为退款申请设计幂等键，重复请求不能产生重复副作用。
- [x] 保留 LangGraph 作为业务流程控制器。

**交付结果：**正常、拒绝、越权、重复提交都有明确结果。

### 阶段二：人工客服工作台与流程恢复

人工暂停、客服审核与补充信息、持久化恢复记录和显式管理员初始化已合并，相关测试与 CI 已通过。完整检索证据和风险原因的业务关联仍待完善；当前仍是单机模拟，未接真实退款。

- [x] 使用 LangGraph `interrupt` 暂停需要人工处理的流程。
- [x] 批准或拒绝后使用 `Command` 恢复；要求补充信息时保持暂停，等待用户回复。
- [x] 复用 `AsyncSqliteSaver` 保存 checkpoint，验证服务重启后的恢复边界。
- [x] 增加客服工单列表和工单详情页。
- [x] 展示会话历史、Agent 摘要和已有工具结果。
- [ ] 将实际知识检索证据和风险原因关联到退款工单。
- [x] 增加客服身份、权限和操作记录。
- [x] 防止重复审批、重复恢复和跨用户访问。

**交付结果：**可演示“用户请求 → Agent 暂停 → 客服审批 → Agent 恢复 → 最终结果”。

### 阶段三：管理员平台与审计

本地实现已加入管理员工作区、售后审计和运行元数据；尚待完整验证、CI 和合并，暂不标记完成。运行记录为尽力写入，历史运行及完整决策证据暂不覆盖。

- [ ] 增加管理员角色和权限边界。
- [ ] 查看用户、客服、工单和流程状态。
- [ ] 查看 Agent 节点、工具调用、失败原因和降级结果。
- [ ] 查看合规命中、人工操作和退款操作审计日志。
- [ ] 增加失败工单和待处理工单统计。

**交付结果：**管理员能回答“谁在什么时候对哪个订单做了什么操作，以及 Agent 为什么这样决定”。

### 阶段四：知识库子 Agent 从 mock RAG 升级为企业知识服务

RAG 不需要删除，但要从“几篇 Markdown + 向量检索”升级为可追溯的知识服务。

- [ ] 使用真实结构的售后政策、会员规则和物流规则替换简单 mock 文本。
- [ ] 为文档增加来源、版本、生效时间、适用范围和发布状态。
- [ ] 增加文档版本管理和失效文档处理。
- [ ] 检索结果必须带来源和引用片段。
- [ ] 使用关键词与向量混合检索，必要时再重排序。
- [ ] 检索不到、规则冲突或置信度不足时拒答或转人工。
- [ ] 单独评测召回率、引用正确率、拒答准确率和转人工准确率。

**交付结果：**回答能指出依据哪份政策、哪个版本、哪一条规则。

### 阶段五：可观测性、故障恢复与回归评测

- [ ] 为每次请求生成 trace ID。
- [ ] 记录节点耗时、模型调用次数、工具调用、错误和降级原因。
- [ ] 覆盖 MCP 超时、LLM 非法 JSON、Redis 不可用、审批后重启和重复提交。
- [ ] 版本化评测集，覆盖正常、越权、拒答、转人工、恢复和幂等场景。
- [ ] 保存运行环境、模型配置、样本规模、结果和失败案例。
- [ ] 只在有前后对照数据时报告优化效果。

**交付结果：**每次演示和回归都能解释系统做了什么、哪里失败、如何恢复。

### 阶段六：小范围引入 Pi

Pi 只用于知识库问答子 Agent，作为可对比实验，不替换主业务流程。

- [ ] 新增独立的 Pi 知识助手实验目录。
- [ ] 让 Pi 负责选择检索工具、组合多个知识来源和生成带引用的答案。
- [ ] 通过稳定 API 或 MCP 调用 Python 知识库服务。
- [ ] 保留 LangGraph 负责退款、审批、中断、恢复、权限、幂等和审计。
- [ ] 对比 Pi 与现有实现的质量、引用正确率、延迟、成本和故障行为。
- [ ] 只有在结果更好且维护成本可接受时，才扩大 Pi 的使用范围。

**交付结果：**能解释为什么 Pi 适合知识 Agent，以及为什么业务工作流仍由 LangGraph 控制。

## 推荐的最终架构

```text
用户端
  ├── 客服工作台
  └── 管理员平台
          ↓
Python FastAPI
  ├── LangGraph 业务工作流
  ├── 权限、状态机、幂等和审计
  ├── 订单/退款服务
  └── 知识库 API / MCP
          ↑
Pi 知识库子 Agent（实验性）
```

## 暂不做

- 不为了追新框架把 LangGraph 主流程整体迁移到 Pi。
- 不同时增加多个业务领域，先做深退款/售后。
- 不把 mock 订单或小样本评测描述成生产能力。
- 不先做复杂配置中心、工作流编排器或多租户平台。
- 不用增加 Agent 数量代替业务规则、权限和恢复能力。

## 面试演示主线

```text
用户申请退款
→ Agent 查询订单并判断需要人工
→ 流程暂停，客服工作台出现工单
→ 客服批准
→ 服务重启后恢复 checkpoint
→ 退款接口幂等执行
→ 管理员查看完整审计记录
```

这条链路完成后，项目的核心卖点是可靠的业务 Agent 工作流，而不是又一个能聊天的客服机器人。
