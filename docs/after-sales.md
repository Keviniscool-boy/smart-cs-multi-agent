# 售后演示业务

当前是基于 SQLite 的单机演示，不连接真实订单或支付系统。每个登录用户首次查看订单时会生成各自的演示订单；数据保存在 `data/after_sales.sqlite3`，不同账号的订单互不可见。演示数据库与账户数据库需要一起持久化；删除后会重新生成演示数据。

## 业务规则与状态

- 已签收的普通商品无理由退货申请超过 7 天会被拒绝；质量问题不套用此期限。取消或未签收的订单不能提交。
- 类型不明、商品分类不明、签收时间异常或模拟政策不可用时进入人工审核。所有已创建的申请均需人工审核，不能声称已批准或已退款。
- 新演示订单标记为普通商品；升级前的订单没有类型，需要人工核实。政策文件及其版本用于演示，不代表真实企业政策。
- 每张订单最多有一个待审核申请；已有通过审核或已完成的申请时不能重新申请。申请和关联工单在同一事务中创建；退款申请初始为 `pending_review`，工单为 `pending`。
- 用户可以撤回自己的待审核申请，申请和工单同时变为 `cancelled`；撤回后可以发起新的申请。

## 人工客服阶段（阶段二）

- 通过 Agent 聊天创建的待审核申请会把图流程暂停在 `human_review` 节点（LangGraph `interrupt`）；面板直接创建的申请没有关联图线程，客服仍可审核其状态。
- 具备 `agent` 或 `admin` 角色的账号在"客服工作台"查看申请：交接单（Agent 摘要、用户原话、工具结果）、会话历史、操作审计。普通用户访问工作台一律 403。
- 客服可以批准、拒绝或要求补充信息。要求补充信息后，客户在订单售后页面提交回复，工单回到待审核；等待补充期间客户也可以撤回申请。
- 批准或拒绝后，决定和恢复记录同时落库，再通过 `Command(resume=...)` 恢复对应图。失败时工作台提供“重试会话恢复”；已完成的恢复不会再次发送通知。批准只代表审核通过，没有执行真实退款。
- 会话处于人工暂停期间，新聊天请求返回 409，避免覆盖暂停点；需要补充信息时使用订单售后页面。

## 初始化管理员

公开注册只创建普通用户，不会自动授予管理员权限。部署者先注册账号，再通过有主机或容器管理权限的终端执行：

```bash
docker compose exec app python -m auth.bootstrap_admin <已注册的用户名>
```

本机部署可执行 `python -m auth.bootstrap_admin <用户名>`。该命令只提升已存在的账户；管理员登录后可通过角色接口授予客服权限。角色变化后刷新页面。升级已有数据库时不会自动调整已有账号的角色，部署者应自行核对既有管理员。

## 身份和接口

接口需要登录，用户身份来自服务端验证的登录态，不采用请求体中的用户 ID。订单和退款申请不存在或不属于当前用户时，返回相同的 404，避免泄露其他账户的数据。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/orders` | 查看自己的演示订单 |
| `GET /api/orders/{order_id}` | 查看自己的订单 |
| `GET /api/refunds` | 查看自己的申请及关联工单号 |
| `POST /api/refunds` | 申请退款，JSON 字段为 `order_id`、`reason` 和可选的 `application_type`（`no_reason` 或 `quality_issue`）；缺省时转人工 |
| `POST /api/refunds/{refund_id}/cancel` | 撤回待审核申请 |
| `POST /api/refunds/{refund_id}/information` | 提交客服要求的补充信息，JSON 字段为 `content` |
| `GET /api/workbench/refunds` | 客服查看申请列表 |
| `GET /api/workbench/refunds/{refund_id}` | 客服查看申请详情、交接、补充信息及操作记录 |
| `POST /api/workbench/refunds/{refund_id}/decision` | 客服提交 `approve`、`reject` 或 `need_info` 决定 |
| `POST /api/workbench/refunds/{refund_id}/resume` | 客服重试尚未完成的会话恢复 |
| `POST /api/workbench/refunds/{refund_id}/prepare` | 当退款已创建但业务节点未完成时，客服重试建立暂停点 |
| `POST /api/admin/users/role` | 管理员为已注册账户设置角色 |

申请接口必须带 `Idempotency-Key` 请求头。一次逻辑请求的重试应使用同一个键；同一用户以相同键和内容（含申请类型）重试会返回原申请的当前状态，相同键对应不同内容返回 409。撤回后的旧请求重试不会创建新申请；用户主动重新申请时需使用新键。同订单已有待审核申请时，相同原因及类型会关联到该申请，否则返回 409。

业务错误包含 `error` 和 `message`：订单或申请无权访问返回 404，幂等键冲突、已有不同原因的申请或不可撤回状态返回 409，参数无效或不符合演示规则返回 400。MCP 和本地备用路径复用相同业务逻辑；内部 MCP 服务依赖调用方提供可信用户身份，不能直接暴露给不可信客户端。

## 当前边界

- 政策为模拟数据。Markdown 政策在启动建索引时按发布状态、版本和日期筛选；修改或下线文件后需要重启完成索引同步。同步失败时暂停知识检索，避免使用旧规则。
- 聊天展示的是检索到的原文片段，并不代表已自动验证模型回答的每一项陈述。现有 `.txt` 文档仍作为普通演示资料加载，不具备政策版本过滤。
- 尚无真实退款或支付对账；客服审核结果不能当作退款到账证明。
- SQLite 和模拟订单适合单机演示；没有多实例业务数据库、完整审计或生产级权限体系。
- 升级时会检查同一订单是否已有多条待审核或已批准的申请；若历史数据冲突，数据库索引初始化会失败，需要先备份并人工核对，不会自动删除记录。
- 恢复记录保存在售后 SQLite 数据库中，checkpoint 保存在独立的 SQLite 文件中，需一起持久化。异常后恢复需要客服在工作台主动重试；运行中租约在 5 分钟后可再次领取。没有分布式队列或自动重试服务。
- 申请的独立幂等键用于防止重试导致重复申请，不代表未来支付渠道的退款执行已经具备幂等保障。
